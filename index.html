tin SDK

Мост между приложением, открытым на https://tin.bar/<id>, и самим tin.bar. Один скрипт без зависимостей: пользователь, тема, язык, вход через кошелёк, подписанные данные пользователя для бэкенда (как initData в Telegram) и общая история браузера.

Приложение tin.bar открывает в <iframe>. SDK общается с родительским окном через window.postMessage и даёт приложению:

  • контекст — приложение, пользователь (или гость), тема и язык интерфейса tin.bar;
  • события — когда пользователь входит/выходит, меняет тему или язык;
  • вход — просьба к tin.bar открыть вход через кошелёк;
  • initData — пользователь, подписанный ключом вашего приложения: бэкенд проверяет подпись сам, без запросов к tin.bar;
  • навигацию — страницы приложения становятся частью адреса tin.bar, кнопки «назад» и «вперёд» работают без единой строчки кода;
  • место под кнопки tin.bar — экран целиком отдан приложению, а SDK говорит, сколько места сверху занимают кнопки tin.bar;
  • обновление мимо кеша — после деплоя приложение загружается таким, каким его отдаёт сервер сейчас.

Подключение

Подключите скрипт с tin.bar на каждой странице приложения:

<script src="https://tin.bar/sdk/tin.js"></script>

После загрузки появляется глобальный объект window.Tin. Повторное подключение (например, два тега <script>) безопасно: остаётся первая копия.

Загружайте SDK именно с tin.bar

SDK общается только с тем origin, с которого он загружен (Tin.hostOrigin). Если положить копию tin.js на свой домен и подключить её через src, SDK будет ждать ответов от вашего домена. Такая копия отклоняет все вызовы с кодом wrong_host и пишет причину в консоль. Копию с домена приложения SDK распознаёт во всех браузерах, а копию с CDN и приложение не на tin.bar — в Chrome и Safari.

Локальная разработка tin.bar

Если tin.bar запущен локально, подключайте SDK с dev-сервера — Tin.hostOrigin автоматически станет его origin.

Быстрый старт

<script src="https://tin.bar/sdk/tin.js"></script>
<script>
  Tin.init()
    .then(({ app, user, theme, locale, initData }) => {
      // user: { id, name } или null для гостя; initData — для вашего бэкенда
      render(user)
    })
    .catch((error) => {
      if (error.code === 'not_embedded') {
        // Страница открыта не внутри tin.bar — например, напрямую по адресу хостинга
      }
    })

  // Пользователь вошёл или вышел
  const off = Tin.on('user', (user) => render(user))

  document.querySelector('#login').onclick = () => Tin.login()
</script>

Вне tin.bar (страница открыта напрямую, не во фрейме) init() отклоняется с кодом not_embedded, а навигация работает как обычно — приложение можно разрабатывать и открывать отдельно.

Кнопки tin.bar висят поверх приложения в правом верхнем углу. Одна строка CSS оставляет под ними место — подробнее в разделе Кнопки tin.bar:

body { padding-top: var(--tin-content-safe-area-inset-top, 0px) }

Свойства

Свойства только для чтения. app, user, theme и locale равны null, initData — пустой строке, contentSafeAreaInset — нулям, а controlsRect — null, пока init() не подключился. Затем они обновляются вместе с событиями.

Tin.init()

Tin.init(): Promise<{ app, user, theme, locale, initData, startParam, canGoBack, contentSafeAreaInset, controlsRect }>

Подключается к tin.bar и возвращает текущий контекст. После успешного вызова значения доступны и как Tin.app, Tin.user, Tin.theme, Tin.locale, Tin.initData, Tin.contentSafeAreaInset и т.д., на <html> появляются CSS-переменные --tin-content-safe-area-inset-* и --tin-controls-*, а SDK начинает синхронизировать адрес и историю с tin.bar.

  • Можно вызывать сколько угодно раз: подключение одно, а каждый вызов получает копию текущего контекста.
  • Если вызов завершился ошибкой, следующий init() попробует подключиться заново.
  • Отклоняется с not_embedded вне tin.bar, с wrong_host, если SDK загружен не с tin.bar, и с timeout, если tin.bar не ответил за 10 секунд.
const { app, user, theme, locale } = await Tin.init()
console.log(app.id, user ? user.name : 'гость')

Tin.on(event, listener)

Tin.on(event: 'user' | 'theme' | 'locale' | 'initData' | 'canGoBack' | 'contentSafeAreaInset' | 'controlsRect', listener: (data) => void): () => void

Подписывается на изменения. Возвращает функцию отписки. Перед вызовом слушателя SDK уже обновил соответствующее свойство (Tin.user и т.д.). Ошибка внутри слушателя не ломает остальных — она пишется в консоль.

Неизвестное имя события сразу бросает исключение с кодом unknown_event.

const unsubscribe = Tin.on('theme', (theme) => {
  document.documentElement.dataset.theme = theme
})

// позже
unsubscribe()
Совет

Подписывайтесь до или сразу после init(): начальные значения приходят в результате init(), а события — только при последующих изменениях.

Tin.login()

Tin.login(): Promise<void>

Просит tin.bar открыть вход через кошелёк. Промис разрешается, когда tin.bar принял просьбу, — не когда пользователь вошёл. Вошедший пользователь приходит в событии 'user'.

Tin.on('user', (user) => {
  if (user) showProfile(user)
})

loginButton.onclick = () => Tin.login()

Tin.initData

Tin.initData: string

Пользователь и время подписи, подписанные tin.bar ключом вашего приложения, — как initData в Telegram Mini Apps. По ней ваш бэкенд проверяет, кто пользователь: подделать её без ключа нельзя. Для гостя — пустая строка. Как проверять — в разделе Авторизация на бэкенде.

async function loadItems() {
  // Гость: без initData бэкенд ответит 401, запрос не отправляем
  if (!Tin.initData) return null
  const response = await fetch('https://your.backend/items', {
    // Как передавать — решает ваш бэкенд, см. «Как передавать initData»
    headers: { Authorization: 'tin ' + Tin.initData },
  })
  return response.json()
}

// login() только открывает окно входа и не ждёт его. Вошедший пользователь
// придёт в событии 'user' — тогда initData уже подписана и можно повторить запрос
loginButton.onclick = () => Tin.login()
Tin.on('user', (user) => {
  if (user) loadItems()
})
Читайте при каждом запросе

tin.bar подписывает initData заново каждые 10 минут и при смене пользователя, а SDK сам обновляет Tin.initData. Не сохраняйте её в переменную при старте.

Пользователь есть, а initData пустая

Так бывает, если tin.bar не смог подписать данные (например, пропала сеть): он повторит попытку сам. Гость — это Tin.user === null. Когда подпись будет готова, придёт событие 'initData'.

Tin.on('initData', (initData) => {
  if (initData) loadItems()
})

Параметр запуска: startapp

Как start_param в Telegram. Ссылка https://tin.bar/<id>?startapp=promo_42 открывает приложение, а значение попадает в Tin.startParam и в подписанную initData (start_param). Бэкенд может ему доверять: так удобно считать рефералов и открывать нужный экран. Допустимы латиница, цифры, _ и -, до 512 символов.

if (Tin.startParam === 'promo_42') showPromo()

// на бэкенде, после проверки подписи:
// new URLSearchParams(initData).get('start_param')   // 'promo_42'

Tin.openApp(id)

Tin.openApp(id: string): Promise<void>

Открывает другое приложение на tin.bar по его id — то же, что перейти на tin.bar/<id>.

Tin.openApp('demo')   // откроет https://tin.bar/demo

Tin.reload()

Tin.reload(): Promise<void>

Загружает приложение заново мимо кеша браузера — то же, что пункт «Обновить кэш» в меню tin.bar. SDK переспрашивает у сервера файлы страницы (скрипты, стили и то, что они загружают), затем перезагружает её. Промис разрешается, когда страница уже перезагружается. Работает и вне tin.bar. Как это устроено — в разделе Обновление и кеш.

updateButton.onclick = () => Tin.reload()   // свежие файлы с сервера
reloadButton.onclick = () => location.reload()   // обычная перезагрузка, SDK не нужен

Когда приходит 'user', Tin.initData уже подписана для нового пользователя: в слушателе можно сразу идти на бэкенд.

Tin.on('user', async (user) => {
  render(user)
  if (user) await loadItems()   // запрос уйдёт с новой Tin.initData
})

Авторизация на бэкенде

Не доверяйте Tin.user на сервере

Tin.user приходит со страницы, а не с сервера. Используйте его для интерфейса, но никогда — для проверки прав. Для этого есть Tin.initData.

Схема та же, что у Telegram Mini Apps: у каждого приложения есть секретный ключ, tin.bar подписывает им данные пользователя, а ваш бэкенд проверяет подпись тем же ключом — сам, без запросов к tin.bar.

  1. Владелец приложения берёт ключ в приложении «Apps» (tin.bar/apps → своё приложение → «Показать ключ») и кладёт его на свой сервер.
  2. Когда пользователь открывает приложение, tin.bar подписывает его ключом приложения и отдаёт в Tin.initData.
  3. Приложение прикладывает строку Tin.initData к запросам на свой бэкенд — как удобно вам: в заголовке, в теле запроса или в параметре адреса (см. Как передавать initData).
  4. Бэкенд проверяет подпись ключом и время подписи и доверяет user.id.

Как передавать initData

tin.bar не диктует способ: initData — обычная строка, и как она попадёт на ваш сервер, решаете вы. Бэкенду нужно одно — получить её целиком и без изменений: подпись считается по этой строке, и любая правка (обрезка, перекодировка, разбор и сборка заново) ломает проверку.

// 1. Заголовок — вариант по умолчанию
fetch('https://your.backend/items', {
  headers: { Authorization: 'tin ' + Tin.initData },
})

// 2. Тело запроса
fetch('https://your.backend/items', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ initData: Tin.initData, title: 'Новая запись' }),
})

// 3. Параметр адреса — только через encodeURIComponent
new WebSocket('wss://your.backend/live?initData=' + encodeURIComponent(Tin.initData))
  • Заголовок — лучший вариант по умолчанию: работает для любых запросов, включая GET, и не попадает в логи адресов. Имя схемы tin — просто договорённость, её используют примеры на этой странице. Подойдёт и свой заголовок, например X-Tin-Init-Data; для запроса на другой домен разрешите его в CORS.
  • Тело запроса — если API и так принимает JSON в POST.
  • Параметр адреса — когда заголовок не передать: WebSocket, EventSource, ссылка на файл. Строка сама состоит из & и =, поэтому без encodeURIComponent она развалится на отдельные параметры. Адрес оседает в логах серверов и прокси, а пока initData не устарела, по ней можно выдать себя за пользователя — используйте этот способ, только если другого нет.

Как бы строка ни пришла, проверка одна и та же: функция verifyInitData() из примеров ниже принимает её как есть. В примере для Express она читается из заголовка — если вы передаёте её иначе, достаньте её оттуда (req.body.initData, req.query.initData).

Своя сессия вместо initData в каждом запросе

Можно проверить initData один раз — например, в запросе входа — и выдать свою сессию (cookie, токен). Тогда сессия не должна жить дольше, чем вы готовы верить auth_date, а приложению стоит сбрасывать её и входить заново, когда в событии 'user' приходит другой пользователь или null.

Формат и проверка

initData          = auth_date=<unix, сек>&user=<JSON { id, name }>[&start_param=…]&hash=<hex>   (query-строка)
data_check_string = строки "key=value" всех полей, кроме hash, отсортированные как строки, через "\n"
secret            = HMAC_SHA256(key = "TinAppData", data = ключ приложения)
hash              = hex(HMAC_SHA256(key = secret, data = data_check_string))
  • Сравнивайте hash за постоянное время (timingSafeEqual, hmac.compare_digest).
  • Отклоняйте старую auth_date: час — хороший предел (tin.bar подписывает данные заново каждые 10 минут).
  • Подпись одного приложения не подходит другому: у каждого свой ключ, поэтому проверять id приложения не нужно.
  • Новые поля, если они появятся, тоже входят в data_check_string — примеры ниже их уже учитывают.

Пример: Node.js (Express)

const crypto = require('node:crypto')
const express = require('express')

const APP_KEY = process.env.TIN_APP_KEY   // ключ приложения из tin.bar/apps
const MAX_AGE_SEC = 3600

// Пользователь { id, name }, если initData подписана ключом приложения и не устарела; иначе null.
function verifyInitData(initData) {
  const params = new URLSearchParams(initData)
  const hash = Buffer.from(params.get('hash') || '', 'hex')
  params.delete('hash')
  const dataCheckString = [...params]
    .map(([key, value]) => key + '=' + value)
    .sort()
    .join('\n')
  const secret = crypto.createHmac('sha256', 'TinAppData').update(APP_KEY).digest()
  const expected = crypto.createHmac('sha256', secret).update(dataCheckString).digest()
  if (hash.length !== expected.length || !crypto.timingSafeEqual(hash, expected)) return null

  const age = Date.now() / 1000 - Number(params.get('auth_date'))
  if (!(age < MAX_AGE_SEC && age > -60)) return null
  return JSON.parse(params.get('user'))
}

function tinAuth(req, res, next) {
  const header = req.get('Authorization') || ''
  const user = header.startsWith('tin ') ? verifyInitData(header.slice(4)) : null
  if (!user) return res.sendStatus(401)
  req.user = user   // { id, name }
  next()
}

const app = express()
app.get('/items', tinAuth, (req, res) => {
  res.json(getItemsOf(req.user.id))
})

Пример: Python

import hashlib, hmac, json, time
from urllib.parse import parse_qsl

# Пользователь {id, name}, если initData подписана ключом приложения и не устарела; иначе None.
def verify_init_data(init_data: str, app_key: str, max_age: int = 3600):
    fields = dict(parse_qsl(init_data))
    received = fields.pop('hash', '')
    data_check_string = '\n'.join(sorted(f'{k}={v}' for k, v in fields.items()))
    secret = hmac.new(b'TinAppData', app_key.encode(), hashlib.sha256).digest()
    expected = hmac.new(secret, data_check_string.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, received):
        return None
    age = time.time() - int(fields['auth_date'])
    if not -60 < age < max_age:
        return None
    return json.loads(fields['user'])
Ключ — секрет

Храните ключ только на сервере. Если он утёк, создайте новый в «Apps» («Новый ключ»): tin.bar сразу начнёт подписывать initData новым ключом, а проверка старым перестанет проходить.

Ссылки и «назад»

После того как init() подключился, страница приложения становится частью адреса tin.bar:

https://tin.bar/<id>/<ваш путь>?<query>#<hash>

Открытие такой ссылки загружает именно эту страницу приложения — ей можно делиться.

Если приложение хранит страницу в hash (сайт из одного файла, createWebHashHistory, HashRouter), hash попадает в адрес tin.bar как есть: index.html#/items/5 → https://tin.bar/<id>#/items/5. Настраивать ничего не нужно; корень такого приложения (#/) — стартовая страница, в адрес он не пишется.

Как устроена история

История принадлежит tin.bar: каждая новая страница приложения становится записью во вкладке tin.bar, а само приложение остаётся на одной записи. Поэтому:

  • кнопки браузера «назад» и «вперёд» ходят по страницам приложения;
  • история переживает перезагрузку страницы;
  • «назад» на первой странице приложения уводит обратно в tin.bar.

Ничего вызывать не нужно — подключите SDK на каждой странице и вызовите init(). history.back(), history.forward() и history.go() продолжают работать: их выполняет tin.bar.

Что SDK перехватывает

Действие в приложенииЧто происходит
history.pushState()Превращается в replaceState во фрейме; tin.bar добавляет новую запись во вкладку.
history.replaceState()Выполняется как обычно; tin.bar обновляет текущий адрес. Частые вызовы (поиск, синхронизированный с адресом, скролл) доходят до tin.bar не чаще раза в 100 мс — последний побеждает.
history.back() / forward() / go(n)Выполняет tin.bar в своей вкладке.
Клик по ссылке на другую страницу того же сайта (и внутри веб-компонента)Открывается как новая запись tin.bar — когда страница загрузилась, как в браузере. Скачивание файла или ответ 204 записи не добавляют, а «назад» во время медленной загрузки останавливает её.
location.assign(), location.hash = …, navigation.navigate()Открывается как новая запись tin.bar, если браузер поддерживает Navigation API: SDK отменяет push и повторяет его как replace (промисы исходного вызова navigation.navigate() при этом отклоняются с AbortError, страница всё равно открывается). Иначе выполняется нативно: запись принадлежит фрейму, а tin.bar только следит за адресом.

Что SDK не трогает

  • клики, которые приложение уже обработало (event.preventDefault(), например ссылки роутера);
  • клики с модификаторами (Ctrl, ⌘, Shift, Alt) и не левой кнопкой;
  • ссылки с target, отличным от _self, и ссылки с атрибутом download;
  • ссылки на другие сайты;
  • отправку форм и загрузки файлов;
  • всё, что происходит до подключения init() и вне tin.bar.

Состояние записи и своя кнопка «назад»

То, что приложение кладёт в запись (history.pushState(state, …), replaceState), tin.bar хранит в своей записи и возвращает при «назад» и «вперёд»: в history.state и в событии popstate. Роутер восстановит позицию скролла и всё, что хранит в состоянии. После перезагрузки страницы история фрейма начинается заново, как и без tin.bar.

Кнопку «назад» внутри приложения показывайте по Tin.canGoBack: на первой странице приложения «назад» уведёт на tin.bar.

const backButton = document.querySelector('#back')
backButton.hidden = !Tin.canGoBack
Tin.on('canGoBack', (canGoBack) => (backButton.hidden = !canGoBack))
backButton.onclick = () => history.back()

Одностраничные приложения (SPA)

Если приложение использует History API (React Router, Vue Router и т.п.), при переходе «назад»/«вперёд» в tin.bar SDK меняет адрес без перезагрузки и отправляет событие popstate — роутер отрисует нужную страницу сам. Многостраничные сайты при этом просто загружают нужную страницу.

Роутеры на Navigation API (navigation.addEventListener('navigate', …) с intercept()) тоже работают: такой роутер получает переход уже как replace и показывает страницу без загрузки.

Одностраничным SDK считает приложение после первого history.pushState(). Одного replaceState() для этого мало: его вызывают и обычные сайты, например аналитика, когда убирает utm_* из адреса. До первого pushState() «назад» загружает страницу заново — это медленнее, но работает везде.

Кнопки tin.bar

Экран целиком отдан приложению: полосы с заголовком над ним нет. Свои кнопки tin.bar кладёт поверх приложения — капсулой в правом верхнем углу, как у мини-приложений Telegram и WeChat: «Ещё», «Свернуть» и «Закрыть». Они видны и пока приложение загружается, так что зависшее приложение всегда можно закрыть.

Tin.contentSafeAreaInset — { top, right, bottom, left } в CSS-пикселях — говорит, как далеко от каждого края фрейма заходят кнопки. Сейчас это полоса сверху: top — её высота, кнопки стоят по её центру у правого края, остальные стороны равны 0. Фон или картинка могут уходить под полосу, а то, что нужно читать или нажимать, держите ниже — или рядом с кнопками, по Tin.controlsRect.

CSS-переменные

Проще всего — переменные, которые SDK ставит на <html>: --tin-content-safe-area-inset-top, -right, -bottom и -left. Они появляются, когда init() подключился, и обновляются сами. Вне tin.bar их нет — указывайте запасное значение.

/* Содержимое начинается под кнопками tin.bar; вне tin.bar отступа нет */
body { padding-top: var(--tin-content-safe-area-inset-top, 0px) }

/* Липкая шапка: её фон уходит под кнопки, а содержимое — ниже них */
header.top {
  position: sticky; top: 0;
  padding-top: var(--tin-content-safe-area-inset-top, 0px);
}

Из JavaScript

function layout(inset) {
  canvas.style.marginTop = inset.top + 'px'
}
Tin.init().then(({ contentSafeAreaInset }) => layout(contentSafeAreaInset))
Tin.on('contentSafeAreaInset', layout)   // tin.bar сменил размер интерфейса

Шапка рядом с кнопками

Шапку приложения можно поставить прямо в полосу — рядом с кнопками tin.bar и на одной линии с ними, как у мини-приложений WeChat. Где сами кнопки, говорит Tin.controlsRect — как wx.getMenuButtonBoundingClientRect() в WeChat:

  • { top, right, bottom, left, width, height } в CSS-пикселях от левого верхнего угла фрейма, как у getBoundingClientRect(): right и bottom — тоже координаты, а не отступы от краёв;
  • значения округлены наружу до целых пикселей: прямоугольник накрывает кнопки целиком;
  • null — tin.bar не показывает кнопки поверх приложения, или это старый tin.bar;
  • пока прямоугольник есть, те же значения лежат в CSS-переменных --tin-controls-top, -right, -bottom, -left, -width и -height.

Кнопки стоят по центру полосы, поэтому шапка высотой top + bottom с содержимым по центру оказывается с ними на одной линии. 100% - left — сколько места справа занимают кнопки. Запасные значения в var() дают обычную шапку там, где кнопок нет:

header {
  display: flex;
  align-items: center;
  /* Высотой с полосу и по центру кнопок; без tin.bar — 56px */
  height: calc(var(--tin-controls-top, 28px) + var(--tin-controls-bottom, 28px));
  /* Справа — до кнопок с зазором в 12px; без tin.bar — обычные 16px.
     Проценты в padding считаются от ширины родителя: шапка — во всю ширину страницы */
  padding: 0 max(16px, calc(100% - var(--tin-controls-left, 100%) + 12px)) 0 16px;
}

Так сделана эта страница: на tin.bar её шапка стоит рядом с кнопками, а переключатель темы — слева. Из JavaScript:

const { controlsRect } = await Tin.init()
// { top: 8, right: 1272, bottom: 42, left: 1154, width: 118, height: 34 } или null

// Старая копия SDK этого события не знает: Tin.on() бросил бы unknown_event
if (Tin.features && Tin.features.includes('controlsRect')) {
  Tin.on('controlsRect', (rect) => layoutHeader(rect))   // кнопки сдвинулись
}
Координаты, а не отступы от краёв

Кнопки прижаты к верху, поэтому смена высоты окна (клавиатура на телефоне) controlsRect не меняет. Ширина окна меняет left и right — tin.bar сообщает об этом событием, а CSS-переменные SDK обновляет сам.

Меню, «Свернуть» и «Закрыть»

  • «Ещё» открывает меню: название приложения и сайт, на котором оно на самом деле работает (адрес tin.bar его не показывает), «Обновить», «Обновить кэш» (см. Обновление и кеш), «Скопировать ссылку» и «Поделиться» — там, где у браузера есть системное окно «Поделиться».
  • «Свернуть» уводит на главную tin.bar, а приложение прячет, не выгружая: оно продолжает работать, сохраняет размер и прокрутку. На других страницах tin.bar внизу видна его плашка: нажатие возвращает приложение на ту же страницу, с той же историей и Tin.canGoBack, крестик закрывает его. Пока приложение свёрнуто, его переходы не меняют адрес и историю tin.bar.
  • «Закрыть» — как и любой другой уход со страницы приложения («назад», ссылка) — выгружает его.

Открыто одно приложение за раз: открытие другого заменяет свёрнутое.

Обновление и кеш

В меню «Ещё» два пункта. Делать для них ничего не нужно — их обрабатывает SDK.

Пункт менюЧто происходит
«Обновить»Приложение перезагружает свою страницу на месте, как кнопка обновления браузера (location.reload()): тот же фрейм, та же страница и состояние её записи истории. Браузер переспрашивает у сервера саму страницу.
«Обновить кэш»То же, но сначала SDK переспрашивает у сервера файлы приложения — как Tin.reload().

Зачем обновлять кеш

Пока страница и её файлы выглядят свежими, браузер берёт их из кеша, не спрашивая сервер. Если сервер не присылает Cache-Control, это часы или дни (эвристическая свежесть): после деплоя приложение остаётся старым — и при следующих запусках тоже. Фрейм не переспрашивает сервер даже при повторном открытии, а обычная перезагрузка переспрашивает страницу, но в Chrome — не её скрипты.

Очистить кеш браузера не могут ни tin.bar, ни приложение, но страница может сама переспросить свои файлы. Так и работают «Обновить кэш» и Tin.reload():

  1. SDK собирает файлы страницы с её собственного origin: скрипты (с модулями, которые они импортируют), стили и то, что они загружают (шрифты, картинки), а также страницу, по адресу которой приложение было открыто. Остальные картинки и данные — содержимое приложения, их SDK не трогает.
  2. Для каждого файла — условный запрос (fetch с cache: 'no-cache'): изменившееся скачивается, остальное сервер подтверждает ответом «304 Not Modified».
  3. Затем location.reload() — браузер переспрашивает и саму страницу. Медленный сервер не задерживает перезагрузку больше чем на 3 секунды: файл, на который он не успел ответить, может прийти из кеша.

Свежие копии остаются в кеше, поэтому следующий запуск тоже будет свежим. Если у приложения есть service worker, на эти запросы отвечает он — так, как в нём написано.

Лучше всего — правильные заголовки

Отдавайте HTML с Cache-Control: no-cache, а остальные файлы — под именами, которые меняются вместе с содержимым (так делают сборщики: app.3f9c1a.js). Тогда каждый запуск свежий сам по себе.

Если приложение не отвечает

Приложение без SDK или ещё не подключившееся (init()) tin.bar сразу открывает заново в новом фрейме, а не ответившее за секунду (старая копия SDK, зависшая страница) — через секунду. При «Обновить кэш» к адресу приложения добавляется ?tinReload=…: такого адреса нет ни в одном кеше, и страница приходит с сервера. SDK убирает параметр из адреса страницы, как только загрузится, а в адресе tin.bar он не появляется.

Ошибки

Все промисы SDK отклоняются объектом Error с полем code. Сообщение начинается с Tin: .

codeКогда
not_embeddedСтраница открыта не внутри tin.bar (не во фрейме).
timeouttin.bar не ответил на запрос за 10 секунд.
wrong_hostSDK загружен не с той страницы, внутри которой открыто приложение: копия с домена приложения, CDN или из бандла, либо приложение открыто не на tin.bar (в Chrome и Safari это видно сразу). Причина — в error.message и в консоли.
unknown_eventTin.on() с неизвестным именем события (бросается синхронно).

Другие коды может вернуть сам tin.bar — они передаются в error.code и error.message без изменений.

try {
  await Tin.init()
} catch (error) {
  switch (error.code) {
    case 'not_embedded': showStandaloneMode(); break
    case 'timeout':      showRetryButton();    break
    default:             console.error(error)
  }
}

Протокол postMessage

Для тех, кто пишет свою реализацию или отлаживает обмен сообщениями. Все сообщения содержат tin: 1 — версию протокола.

Приложение → tin.bar

{ tin: 1, id, method, params? }
methodparamsНазначение
init{ href, state? }Подключение; state — что приложение уже хранит в записи страницы. Ответ — { app, user, theme, locale, initData, startParam, canGoBack, contentSafeAreaInset, controlsRect } и служебное navigating: true, если сразу за ним придёт navigate (пользователь прошёл по истории, пока приложение грузилось).
login—Открыть вход через кошелёк.
open{ id }Открыть другое приложение.
location{ href, replace, state?, load? }Адрес фрейма изменился: новая запись (replace: false) или замена текущей. state — состояние записи после pushState/replaceState. load: true — приложение начало загружать страницу по ссылке: tin.bar добавит запись, когда страница придёт (её init или location с этим адресом). Уходить со страницы стоит после ответа на это сообщение: сообщение от страницы, которой уже нет, приходит без event.source, и tin.bar его не примет.
go{ delta }Переход по истории вкладки tin.bar.
reload—Ответ на событие reload: приложение перезагрузится само, создавать фрейм заново не нужно.

tin.bar → приложение

{ tin: 1, id, result }                    // успешный ответ на запрос
{ tin: 1, id, error: { code, message } }  // ошибка
{ tin: 1, event, data }                   // событие

События: user, theme, locale, initData (новая подпись приходит перед user), canGoBack, contentSafeAreaInset, controlsRect (эти два приходят и сразу на init, до ответа: страница не сдвигается после показа) и служебные:

  • navigate: data — адрес, который нужно показать во фрейме без новой записи в истории, state — что приложение хранило в этой записи;
  • reload: пользователь выбрал «Обновить» или «Обновить кэш», data — { refreshCache }. От старого tin.bar приходит null: его единственное обновление шло мимо кеша.

Безопасность

  • SDK отправляет сообщения только на Tin.hostOrigin и принимает их только от родительского окна с этим origin. Сайт, который просто встроил ваше приложение во фрейм, ничего не получит.
  • Tin.user — данные для интерфейса. Права проверяйте на бэкенде по подписи Tin.initData.
  • Ключ приложения храните только на сервере; утёк — создайте новый в «Apps».
  • Отклоняйте старую auth_date: после выхода пользователя уже выданная initData действует, пока вы её принимаете.

Частые вопросы

Можно ли открыть приложение без tin.bar?

Да. Вне фрейма init() отклонится с not_embedded, а навигация и история работают как на обычном сайте. Удобно для разработки.

Нужно ли вызывать init() на каждой странице?

Да, если сайт многостраничный: подключите SDK и вызовите init() на каждой странице — иначе её адрес не попадёт в tin.bar. В SPA достаточно одного вызова при старте.

Почему «назад» ничего не делает?

Скорее всего, запись в истории была создана до подключения init() или браузер не поддерживает Navigation API: такие записи принадлежат фрейму и пропадают при его перезагрузке. Вызывайте init() как можно раньше.

После деплоя приложение показывает старую версию

Браузер взял страницу или её скрипты из кеша. Пункт «Обновить кэш» в меню tin.bar (или Tin.reload()) загрузит их с сервера, а заголовки из раздела Обновление и кеш избавят от этого насовсем.

Что-то в приложении закрыто кнопками tin.bar

Кнопки висят поверх приложения. Оставьте под ними место: padding-top: var(--tin-content-safe-area-inset-top, 0px) — или поставьте шапку рядом с ними по Tin.controlsRect. Подробнее — в разделе Кнопки tin.bar.

Как сделать ссылку на страницу приложения?

Tin.hostOrigin + '/' + Tin.app.id + '/путь'. Внутри приложения используйте обычные относительные ссылки — SDK сам превратит их в записи истории tin.bar.

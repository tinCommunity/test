tin SDK

Мост между приложением, открытым на https://tin.bar/<id>, и самим tin.bar. Один скрипт без зависимостей: пользователь, тема, язык, вход через кошелёк, токен для бэкенда и общая история браузера.

Быстрый стартПодключить SDK и получить пользователя за пять строк. БэкендКак безопасно узнать, кто пользователь, на своём сервере. Ссылки и «назад»Как страницы приложения попадают в адрес и историю tin.bar.

Приложение tin.bar открывает в <iframe>. SDK общается с родительским окном через window.postMessage и даёт приложению:

  • контекст — приложение, пользователь (или гость), тема и язык интерфейса tin.bar;
  • события — когда пользователь входит/выходит, меняет тему или язык;
  • вход — просьба к tin.bar открыть вход через кошелёк;
  • токен — короткоживущий токен, по которому ваш бэкенд проверяет пользователя;
  • навигацию — страницы приложения становятся частью адреса tin.bar, кнопки «назад» и «вперёд» работают без единой строчки кода.

Подключение

Подключите скрипт с tin.bar на каждой странице приложения:

<script src="https://tin.bar/sdk/tin.js"></script>

После загрузки появляется глобальный объект window.Tin. Повторное подключение (например, два тега <script>) безопасно: остаётся первая копия.

Загружайте SDK именно с tin.bar

SDK общается только с тем origin, с которого он загружен (Tin.hostOrigin). Если положить копию tin.js на свой домен и подключить её через src, SDK будет ждать ответов от вашего домена и не подключится к tin.bar.

Локальная разработка tin.bar

Если tin.bar запущен локально, подключайте SDK с dev-сервера — Tin.hostOrigin автоматически станет его origin.

Быстрый старт

<script src="https://tin.bar/sdk/tin.js"></script>
<script>
  Tin.init()
    .then(({ app, user, theme, locale }) => {
      // user: { id, name } или null для гостя
      render(user)
    })
    .catch((error) => {
      if (error.code === 'not_embedded') {
        // Страница открыта не внутри tin.bar — например, напрямую по адресу хостинга
      }
    })

  // Пользователь вошёл или вышел
  const off = Tin.on('user', (user) => render(user))

  document.querySelector('#login').onclick = () => Tin.login()
</script>

Вне tin.bar (страница открыта напрямую, не во фрейме) init() отклоняется с кодом not_embedded, а навигация работает как обычно — приложение можно разрабатывать и открывать отдельно.

Свойства только для чтения. app, user, theme и locale равны null, пока init() не подключился, затем обновляются вместе с событиями.

Tin.init()

Tin.init(): Promise<{ app, user, theme, locale }>

Подключается к tin.bar и возвращает текущий контекст. После успешного вызова значения доступны и как Tin.app, Tin.user, Tin.theme, Tin.locale, а SDK начинает синхронизировать адрес и историю с tin.bar.

  • Можно вызывать сколько угодно раз — все вызовы получат один и тот же промис.
  • Если вызов завершился ошибкой, следующий init() попробует подключиться заново.
  • Отклоняется с not_embedded вне tin.bar и с timeout, если tin.bar не ответил за 10 секунд.
const { app, user, theme, locale } = await Tin.init()
console.log(app.id, user ? user.name : 'гость')

Tin.on(event, listener)

Tin.on(event: 'user' | 'theme' | 'locale', listener: (data) => void): () => void

Подписывается на изменения. Возвращает функцию отписки. Перед вызовом слушателя SDK уже обновил соответствующее свойство (Tin.user и т.д.). Ошибка внутри слушателя не ломает остальных — она пишется в консоль.

Неизвестное имя события сразу бросает исключение с кодом unknown_event.

const unsubscribe = Tin.on('theme', (theme) => {
  document.documentElement.dataset.theme = theme
})

// позже
unsubscribe()
Совет

Подписывайтесь до или сразу после init(): начальные значения приходят в результате init(), а события — только при последующих изменениях.

Tin.login()

Tin.login(): Promise<void>

Просит tin.bar открыть вход через кошелёк. Промис разрешается, когда tin.bar принял просьбу, — не когда пользователь вошёл. Вошедший пользователь приходит в событии 'user'.

Tin.on('user', (user) => {
  if (user) showProfile(user)
})

loginButton.onclick = () => Tin.login()

Tin.token()

Tin.token(): Promise<{ token, expiresAt }>

Выдаёт короткоживущий токен, по которому ваш бэкенд узнаёт, кто пользователь. Для гостя отклоняется с кодом unauthorized. Подробнее — в разделе Авторизация на бэкенде.

try {
  const { token, expiresAt } = await Tin.token()
  await fetch('https://your.backend/items', {
    headers: { Authorization: 'Bearer ' + token },
  })
} catch (error) {
  if (error.code === 'unauthorized') Tin.login()
}

Tin.openApp(id)

Tin.openApp(id: string): Promise<void>

Открывает другое приложение на tin.bar по его id — то же, что перейти на tin.bar/<id>.

Tin.openApp('demo')   // откроет https://tin.bar/demo

После события 'user' старый токен больше не соответствует пользователю — запросите новый через Tin.token().

let token = null

Tin.on('user', async (user) => {
  token = user ? (await Tin.token()).token : null
  render(user)
})

Авторизация на бэкенде

Не доверяйте Tin.user на сервере

Tin.user приходит со страницы, а не с сервера. Используйте его для интерфейса, но никогда — для проверки прав. Для этого есть токен.

  1. Приложение получает токен: await Tin.token().
  2. Отправляет его своему бэкенду в заголовке Authorization: Bearer <token>.
  3. Бэкенд спрашивает tin.bar, чей это токен: GET https://api.tin.bar/v1/apps/session.
  4. Бэкенд проверяет, что app.id — это id вашего приложения, и доверяет user.id.

Клиент

const { token, expiresAt } = await Tin.token()   // 'unauthorized' для гостя
fetch('https://your.backend/items', { headers: { Authorization: 'Bearer ' + token } })

Проверка токена

GET https://api.tin.bar/v1/apps/session
Authorization: Bearer <token>

200 → { "app": { "id": "..." }, "user": { "id": "...", "name": "..." } }
401 → токен недействителен или истёк

Пример: Node.js (Express)

const express = require('express')
const app = express()
const APP_ID = 'my-app'   // id вашего приложения на tin.bar

async function tinAuth(req, res, next) {
  const header = req.get('Authorization') || ''
  if (!header.startsWith('Bearer ')) return res.sendStatus(401)

  const response = await fetch('https://api.tin.bar/v1/apps/session', {
    headers: { Authorization: header },
  })
  if (response.status === 401) return res.sendStatus(401)
  if (!response.ok) return res.sendStatus(502)

  const session = await response.json()   // { app: { id }, user: { id, name } }
  // Токен, выданный другому приложению, не должен работать в вашем
  if (session.app.id !== APP_ID) return res.sendStatus(401)

  req.user = session.user   // { id, name }
  next()
}

app.get('/items', tinAuth, (req, res) => {
  res.json(getItemsOf(req.user.id))
})
Срок жизни токена

Токен короткоживущий — смотрите expiresAt. Когда он истёк, просто вызовите Tin.token() ещё раз. Новый токен нужен и после события 'user'.

// Небольшой помощник: всегда свежий токен в запросе
async function api(path, options = {}) {
  const { token } = await Tin.token()
  return fetch('https://your.backend' + path, {
    ...options,
    headers: { ...options.headers, Authorization: 'Bearer ' + token },
  })
}

Ссылки и «назад»

После того как init() подключился, страница приложения становится частью адреса tin.bar:

https://tin.bar/<id>/<ваш путь>?<query>#<hash>

Открытие такой ссылки загружает именно эту страницу приложения — ей можно делиться.

Как устроена история

История принадлежит tin.bar: каждая новая страница приложения становится записью во вкладке tin.bar, а само приложение остаётся на одной записи. Поэтому:

  • кнопки браузера «назад» и «вперёд» ходят по страницам приложения;
  • история переживает перезагрузку страницы;
  • «назад» на первой странице приложения уводит обратно в tin.bar.

Ничего вызывать не нужно — подключите SDK на каждой странице и вызовите init(). history.back(), history.forward() и history.go() продолжают работать: их выполняет tin.bar.

Что SDK перехватывает

Действие в приложенииЧто происходит
history.pushState()Превращается в replaceState во фрейме; tin.bar добавляет новую запись во вкладку.
history.replaceState()Выполняется как обычно; tin.bar обновляет текущий адрес.
history.back() / forward() / go(n)Выполняет tin.bar в своей вкладке.
Клик по ссылке на другую страницу того же сайтаОткрывается как новая запись tin.bar.
location.assign(), location.hash = …, navigation.navigate()Открывается как новая запись tin.bar, если браузер поддерживает Navigation API. Иначе выполняется нативно: запись принадлежит фрейму, а tin.bar только следит за адресом.

Что SDK не трогает

  • клики, которые приложение уже обработало (event.preventDefault(), например ссылки роутера);
  • клики с модификаторами (Ctrl, ⌘, Shift, Alt) и не левой кнопкой;
  • ссылки с target, отличным от _self, и ссылки с атрибутом download;
  • ссылки на другие сайты;
  • отправку форм и загрузки файлов;
  • всё, что происходит до подключения init() и вне tin.bar.

Одностраничные приложения (SPA)

Если приложение использует History API (React Router, Vue Router и т.п.), при переходе «назад»/«вперёд» в tin.bar SDK меняет адрес без перезагрузки и отправляет событие popstate — роутер отрисует нужную страницу сам. Многостраничные сайты при этом просто загружают нужную страницу.

Ошибки

Все промисы SDK отклоняются объектом Error с полем code. Сообщение начинается с Tin: .

codeКогда
not_embeddedСтраница открыта не внутри tin.bar (не во фрейме).
timeouttin.bar не ответил на запрос за 10 секунд.
unauthorizedTin.token() вызван для гостя.
unknown_eventTin.on() с неизвестным именем события (бросается синхронно).

Другие коды может вернуть сам tin.bar — они передаются в error.code и error.message без изменений.

try {
  await Tin.init()
} catch (error) {
  switch (error.code) {
    case 'not_embedded': showStandaloneMode(); break
    case 'timeout':      showRetryButton();    break
    default:             console.error(error)
  }
}

Протокол postMessage

Для тех, кто пишет свою реализацию или отлаживает обмен сообщениями. Все сообщения содержат tin: 1 — версию протокола.

Приложение → tin.bar

{ tin: 1, id, method, params? }
methodparamsНазначение
init{ href }Подключение; ответ — { app, user, theme, locale }.
login—Открыть вход через кошелёк.
token—Выдать токен; ответ — { token, expiresAt }.
open{ id }Открыть другое приложение.
location{ href, replace }Адрес фрейма изменился: новая запись (replace: false) или замена текущей.
go{ delta }Переход по истории вкладки tin.bar.

tin.bar → приложение

{ tin: 1, id, result }                    // успешный ответ на запрос
{ tin: 1, id, error: { code, message } }  // ошибка
{ tin: 1, event, data }                   // событие

События: user, theme, locale (публичные) и navigate (служебное, data — адрес, который нужно показать во фрейме без новой записи в истории).

Безопасность

  • SDK отправляет сообщения только на Tin.hostOrigin и принимает их только от родительского окна с этим origin. Сайт, который просто встроил ваше приложение во фрейм, ничего не получит.
  • Tin.user — данные для интерфейса. Права проверяйте на бэкенде по токену.
  • На бэкенде всегда сверяйте app.id из ответа /v1/apps/session с id своего приложения.
  • Не храните токен долго: он короткоживущий, запрашивайте новый по мере необходимости.

Частые вопросы

Можно ли открыть приложение без tin.bar?

Да. Вне фрейма init() отклонится с not_embedded, а навигация и история работают как на обычном сайте. Удобно для разработки.

Нужно ли вызывать init() на каждой странице?

Да, если сайт многостраничный: подключите SDK и вызовите init() на каждой странице — иначе её адрес не попадёт в tin.bar. В SPA достаточно одного вызова при старте.

Почему «назад» ничего не делает?

Скорее всего, запись в истории была создана до подключения init() или браузер не поддерживает Navigation API: такие записи принадлежат фрейму и пропадают при его перезагрузке. Вызывайте init() как можно раньше.

Как сделать ссылку на страницу приложения?

Tin.hostOrigin + '/' + Tin.app.id + '/путь'. Внутри приложения используйте обычные относительные ссылки — SDK сам превратит их в записи истории tin.bar.
